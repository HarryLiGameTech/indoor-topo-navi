Cross-Map Transportation

A transport declares traversable connections between topo maps. Because each topo-map instance represents one floor, a transport normally describes movement between floors.

A transport does not replace the landing areas inside floor maps. Each participating map declares its own landing node; a transport station references that node and connects it to the transport network.

  • Common transport model
  • Elevators
  • Escalators
  • Stairs

Topology Boundary

Atomic paths describe movement within one topo map. Transports describe movement between topo maps.

An elevator hall, stair landing, or escalator landing remains an ordinary node in its floor map. Walking to the landing is described by that map's atomic paths. The transport begins and ends at the referenced landing nodes.

Project Inclusion

A transport participates in a building only when selected by building-includes:

building-includes {
  submap Lobby
  submap OfficeLevel2
  vehicle MainElevator
}

vehicle MainElevator resolves MainElevator.ttr, falling back to the extensionless source MainElevator.

Supported Transport Types

transport MainElevator is Elevator {
}

transport AtriumEscalator is Escalator {
}

transport WestStair is Stairs {
}

The supported type names are exactly Elevator, Escalator, and Stairs. They are case-sensitive. Generic, user-defined, and additional transport types are not currently supported.

Common Declaration Model

A transport body may contain:

  • a transport-specific local params record;
  • local let, def, and constraint declarations;
  • an optional string-valued displayName binding;
  • station declarations;
  • station access annotations; and
  • ride-from policies.
transport MainElevator is Elevator {
  let params = {
    maxVelocity = 2.5,
    acceleration = 0.8,
    carAmount = 3
  }

  let displayName = "Main passenger elevators"

  station Lobby at Lobby::main_elevator_landing {
    location = 0.0,
    departureRate = 0.40
  }

  station Office2 at OfficeLevel2::main_elevator_landing {
    location = 4.2,
    departureRate = 0.10
  }
}

Stations and Landing Nodes

station Office2 at OfficeLevel2::main_elevator_landing {
  location = 4.2,
  departureRate = 0.10
}
Office2
A station label local to this transport.
OfficeLevel2
The topo-map instance containing the landing.
main_elevator_landing
The existing node used as the transport endpoint on that map.

A station does not create its referenced map or node. The map must be included in the building and the node must exist in that map.

Station labels should be unique within a transport. They are used by station-specific ride-from policies and are distinct from map identifiers.

Service Range and Direction

The declared stations define the maps served by a transport. An unlisted map is not a stop.

For elevators and stairs, the engine connects every permitted ordered pair of distinct station maps. Declaration order does not limit travel to adjacent stations. An express service is modeled by declaring only the maps at which it stops.

An escalator has a specialized two-station service model described in Escalators.

Station Access

A hard station requirement controls whether an elevator or escalator station may be used for arrival, departure, or both:

station TradingFloor at OfficeLevel50::passenger_landing {
  location = 222.0,
  departureRate = 0.04
} requires TradingFloorAccess on Arrive
Form Effect when the constraint is unsatisfied
requires Access Neither arrival nor departure is permitted.
requires Access on Arrive Arrival is prohibited; departure remains permitted.
requires Access on Depart Departure is prohibited; arrival remains permitted.

A station may be completely disabled:

station F18 at OfficeLevel18::passenger_landing {
  location = 84.0,
  departureRate = 0.04
} out-of-order

out-of-order prohibits both arrival and departure for elevators and escalators. Stair access is modeled differently; see Stair Access Control.

Constraints use root or transport-local declarations and are evaluated during compilation. Changing a supplied parameter requires a separately compiled building model. See Compilation Time and Routing Time.

Uncertain Station Access

subject-to records uncertain station availability without removing the transport from the compiled model:

station Roof at RoofLevel::lift_landing {
  location = 180.0,
  departureRate = 0.05
} subject-to RoofLiftAvailable because "The roof lift may close in severe weather." on Arrive

Routing-time selection, propagation, and disclosure are documented in Uncertain Access and Risk Handling.

Ride Policies

A ride-from declaration controls matching directed rides according to one or more named constraints:

ride-from any to HotelDomain requires HotelAccess
ride-from ServiceLobby to OfficeDomain requires <OfficeAccess && CarryingGoods>

Each operand must be any, a station label declared by this transport, or an effective management-domain name. A topo-map identifier is not a ride-policy operand merely because a station serves that map.

An unsatisfied rule removes matching rides in the declared direction. It does not affect the reverse direction. A satisfied rule permits its matching pairs, subject to station permissions and other applicable rules. A pair not matched by any rule remains permitted; ride-from declarations are not a whitelist.

If several rules match, the rule with the highest specificity applies:

  1. station to station;
  2. station to domain;
  3. domain to station;
  4. domain to domain;
  5. any to station;
  6. station to any;
  7. any to domain;
  8. domain to any;
  9. any to any.

A station label takes precedence over a same-named management domain. Conflicting rules for the same operands and specificity are invalid.

Management-domain attachment and override precedence are defined in Management-Domain Attachment.

Transfers Between Transports

When two transports serve the same topo map, transfer between them requires an intra-map walking route between their landing nodes.

/* Inside OfficeExpress */
station F30 at SkyLobby30::express_landing {
  location = 138.0,
  departureRate = 0.40
}

/* Inside OfficeLocal */
station F30 at SkyLobby30::local_landing {
  location = 138.0,
  departureRate = 0.10
}

The transfer cost is the atomic-path cost of walking from express_landing to local_landing. If no permitted path connects the landing nodes, the transfer is unavailable on that map.

Entry, Exit, Transfer, and Ride Costs

Walking to or from a landing is represented by the floor map's atomic paths. TopoScript does not declare separate transport entry or exit costs.

  • Elevator cost combines estimated waiting time and movement time.
  • Escalator cost is the declared fixed travel time.
  • Stair cost represents climbing time.
  • A same-floor transfer uses the walking cost between landing nodes.

End-to-end route-cost composition and routing preferences belong to the routing reference.

Route Output

Elevator and escalator rides are returned as Transport segments. Stair traversal is returned as Climbing.

Current movement descriptions identify the transport and endpoint maps:

Take MainElevator from Lobby to OfficeLevel2

displayName and station labels are retained in the compiled transport model, while route-step descriptions currently use the transport identifier. Transport-level tags, arbitrary annotation records, required actions, and navigation hints are not supported.

Invalid References and Declarations

  • An unsupported transport type fails parsing or transport elaboration.
  • A station referencing an unknown map or node fails compilation.
  • An unknown station label or management domain in ride-from fails compilation.
  • Duplicate station labels make station-specific policies ambiguous and are invalid.
  • A transport with fewer than two usable station maps cannot provide cross-map movement.
  • Transport-specific missing or incorrectly typed fields fail compilation as described in the specialized articles.

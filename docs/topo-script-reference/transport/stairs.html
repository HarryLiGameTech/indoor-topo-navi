Stairs

A Stairs transport represents a continuous staircase connecting landing nodes on two or more topo-map instances.

Common station, ride-policy, transfer, and output rules are defined in Cross-Map Transportation.

Declaration

transport WestStair is Stairs {
  let params = {
    turnBackCost = 3
  }

  let displayName = "West staircase"

  station Ground at Lobby::west_stair_landing {
    location = 0.0,
    directSegmentIndex = 0
  }

  station Level2 at OfficeLevel2::west_stair_landing {
    location = 4.2,
    directSegmentIndex = 1
  }

  station Level3 at OfficeLevel3::west_stair_landing {
    location = 8.4,
    directSegmentIndex = 2
  }
}

Stair Parameters

A staircase must define a local params record. turnBackCost is an optional Int and defaults to 3.

turnBackCost represents additional traversal time, in seconds, for a change between direct stair segments. It is a time cost rather than a stamina or physical-demand value.

Stair Station Fields

Every stair station requires:

Field Type Meaning
location Int or Float Vertical elevation in metres relative to a consistent building datum.
directSegmentIndex Int The ordered direct stair segment containing this landing.

Indices normally begin at 0 at one end of the staircase and increase as the staircase progresses. Crossing non-adjacent segment indices incurs turnBackCost for the intermediate changes of direction.

Traversal Time

Base stair traversal time is estimated from the absolute vertical difference between station location values using an average vertical walking speed of 0.167 metres per second. Applicable turnBackCost values represent additional traversal time.

Stair traversal is returned as Climbing. Physical-demand routing may therefore penalize stair traversal more heavily than elevator or escalator use without interpreting turnBackCost as a stamina score.

Service Range

Every declared landing is part of the same continuous staircase. The compiled transport connects every permitted ordered pair of distinct station maps; station declarations do not need to be limited to adjacent floors.

Stair Access Control

Stair stations deliberately ignore station-level requires and out-of-order. A person's ability to step onto a stair landing is determined by the surrounding floor topology rather than by the staircase transport itself.

When a staircase is protected by a locked door, staff-only entrance, emergency gate, or similar boundary, attach requires to the atomic path that crosses that boundary:

atomic-path [public_corridor -> protected_stair_landing] {
  cost = 4.0
} requires StaffAccess

This controls the actual doorway or boundary while leaving the physical staircase represented. Where access differs by floor or travel direction, place the requirement on each applicable directed doorway path.

Invalid Stair Declarations

  • The transport must contain a record-valued params binding.
  • turnBackCost, when present, must be an Int.
  • Every station must provide a numeric location.
  • Every station must provide an integer directSegmentIndex.
  • Every qualified station node must resolve to an included topo map and a declared node.
  • A staircase intended for cross-map navigation must serve at least two maps.

Routing Modes and Preferences

A routing mode determines how the building is searched. A route-planning preference determines how eligible transport candidates are ranked within that search.

Request-Body Controls

routePlanningPreference, riskPreference, and banTags are fields of the request body's traversalPreference object. Compilation parameters are fields of userParams.

{
  "userParams": {
    "officeAccess": true
  },
  "traversalPreference": {
    "routePlanningPreference": "MinimizeTime",
    "riskPreference": "conservative",
    "banTags": ["outdoor"]
  }
}

For the full HTTP request format and examples, see the Navigation Request Guide.

Order of Route Decisions

  1. Compilation parameters establish the building's hard-access topology.
  2. Banned tags exclude request-specific nodes and paths.
  3. The risk preference determines whether failed uncertain access may participate.
  4. isHighRise selects the building-routing strategy.
  5. The route-planning preference ranks eligible candidates.
  6. Output annotations describe the selected route.

A route preference cannot restore a path, station, or ride removed by a hard access constraint.

Building-Routing Modes

isHighRise=false
Uses fully informed routing, which compares complete walking and transport costs throughout the building.
isHighRise=true
Uses transport-first routing, which ranks cross-map transport plans before connecting their floor-level walking legs.

The quick-demo endpoint defaults to isHighRise=true. The flag selects an algorithm and does not describe or validate the building's literal height.

See Fully Informed Low-Rise Routing and High-Rise Routing.

Primary Route-Planning Preferences

The supported values are MinimizeTime, MinimizeTransfers, and MinimizePhysicalDemands. The default is MinimizeTime. Unknown values are rejected by the web API.

MinimizeTime

Routes are ranked using their calculated traversal costs.

In fully informed low-rise mode, this preference minimizes complete end-to-end cost.

In high-rise mode, it initially minimizes the transport portion of the journey. Walking to and from the selected transport is included in the returned route but not in the initial transport ranking.

MinimizeTransfers

In high-rise mode, candidates are ordered first by the number of edges in the transport plan and then by total transport-plan cost.

The counted edges include both cross-map rides and same-floor connections between transport lines. The value is therefore a transport-plan hop count, not strictly the number of times a passenger changes vehicles.

In low-rise mode, this preference currently produces the same total-cost search as MinimizeTime.

MinimizePhysicalDemands

High-rise transport candidates use the following relative score:

  • elevator movement: 0.1 × vertical distance;
  • stair movement: 10 × vertical distance;
  • escalator movement: fixed travel time; and
  • walking between transport landings: walking time.

Lower scores are preferred. Origin and destination walking legs are not part of the initial high-rise transport score.

This score is a routing heuristic, not a physiological, medical, energy-expenditure, or accessibility measurement.

In low-rise mode, this preference currently produces the same total-cost search as MinimizeTime.

Preference Summary

Preference Fully informed low-rise mode High-rise mode
MinimizeTime Minimizes complete route cost. Ranks the transport plan by cost before floor-level walking is connected.
MinimizeTransfers Currently minimizes complete route cost. Ranks by transport-plan edge count, then transport cost.
MinimizePhysicalDemands Currently minimizes complete route cost. Ranks by the transport physical-demand heuristic.

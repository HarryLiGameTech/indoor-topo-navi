Routing Modes and Preferences

A routing mode determines how the building is searched. A route-planning preference determines how complete routes are ranked, including all walking, transport, and mandatory intermediate-node dwell.

Request-Body Controls

routePlanningPreference, riskPreference, and banTags are fields of the request body's traversalPreference object. Compilation parameters are fields of userParams.

{
  "userParams": {
    "officeAccess": true
  },
  "traversalPreference": {
    "routePlanningPreference": "MinimizeTime",
    "riskPreference": "conservative",
    "banTags": ["outdoor"]
  }
}

For the full HTTP request format and examples, see the HTTP API reference.

Order of Route Decisions

  1. Compilation parameters establish the building's hard-access topology.
  2. Banned tags exclude request-specific nodes and paths.
  3. The risk preference determines whether failed uncertain access may participate.
  4. routingMode selects the building-routing strategy.
  5. The route-planning preference supplies the search objective and tie-breakers.
  6. Output annotations describe the selected route.

A route preference cannot restore a path, station, or ride removed by a hard access constraint.

Building-Routing Modes

routingMode: "fullyInformed"
Searches individual walking and transport edges throughout the building.
routingMode: "partiallyInformed"
Searches a hierarchy of transport landings and the exact endpoints. Floor-level walking connections are computed on demand, and their full costs participate in route selection.

The HTTP API defaults to partiallyInformed. Both modes support the same objectives; the mode does not describe or validate the building's literal height. Core callers select the corresponding strategy with isHighRise.

See Fully Informed Low-Rise Routing and High-Rise Routing.

Primary Route-Planning Preferences

The supported values are MinimizeTime, MinimizeTransfers, MinimizePhysicalDemands, and MinimizeCustomData. The default is MinimizeTime. Unknown values are rejected by the web API.

MinimizeTime

Minimizes complete end-to-end traversal time in either routing mode, including walking to and from transports and mandatory intermediate-node dwell.

MinimizeTransfers

Minimizes actual transport-line changes, then complete end-to-end traversal time, in either routing mode.

Walking-only routes and trips on a single line count as zero transfers. Switching to another line adds one, including when walking connects the lines; consecutive rides on the same line add none.

MinimizePhysicalDemands

Both routing modes minimize the following complete-route score, then traversal time:

  • elevator movement: 0.1 × vertical metres + 0.5 × seconds;
  • stair movement: 10 × vertical metres;
  • escalator movement: 0.1 × distance metres + 0.65 × seconds; and
  • walking and mandatory intermediate-node dwell: elapsed seconds.

Lower scores are preferred. Elevator seconds include waiting and movement. Escalator metres come from optional params.distance, defaulting to zero when omitted. Origin, destination, and transfer walking all participate in route selection.

This score is a routing heuristic, not a physiological, medical, energy-expenditure, or accessibility measurement.

MinimizeCustomData

Minimizes an additive custom cost as the primary objective in either routing mode. Equal custom costs are resolved by transport-line changes, then total time. Set tieBreakers to reverse that order; both criteria must appear exactly once.

"traversalPreference": {
  "routePlanningPreference": "MinimizeCustomData",
  "customObjective": {
    "kind": "tagExposure",
    "tag": "outdoor",
    "tieBreakers": ["MinimizeTransfers", "MinimizeTime"]
  }
}

tagExposure sums tagged-edge traversal seconds and explicit dwell at tagged intermediate nodes. Alternatively, edgeAttribute sums a named numeric atomic-path attribute:

"customObjective": {
  "kind": "edgeAttribute",
  "attribute": "effort",
  "missingValue": 0
}

Attribute values must be finite, non-negative Int or Float values. Missing values use missingValue, which defaults to zero. Transport rides contribute zero to this attribute sum; transport parameters and node attributes are not included. Invalid selected attribute data returns INVALID_ROUTING_DATA.

This mode has no near-tie tolerance and cannot be combined with minimizeTag. An absent tag gives every route zero exposure, so the configured tie-breakers decide. See the HTTP API reference for validation and response fields.

Soft Tag Avoidance

traversalPreference.minimizeTag selects the least-exposed route within the primary objective's tolerance: 60 extra seconds, two extra transport-line changes, or 25% extra physical demand. Ties use the primary score, total time, and canonical route order. Hard access constraints and tag bans still apply.

Tagged edges contribute traversal seconds; tagged intermediate nodes contribute explicit minDwellSeconds. Mandatory intermediate-node dwell always adds to time and physical demand, even without a soft preference. Endpoint dwell is excluded.

The primary route uses the selected routing mode. If it has zero exposure, it is already optimal and no additional search runs. Otherwise a constrained complete-route search selects the least exposure inside the tolerance. That additional search can still be expensive. Native custom optimization does not require this tolerance-constrained search.

Every objective includes all walking and transport. The primary search, floor-level connections, and any subsequent soft-tag search share a limit of 50,000 generated labels and 200,000 edge expansions. Exceeding a limit returns HTTP 503 with TRAVERSAL_PREFERENCE_SEARCH_LIMIT.

maximizeTag remains deferred. See the finalized Traversal Preference Spec for the complete contract.

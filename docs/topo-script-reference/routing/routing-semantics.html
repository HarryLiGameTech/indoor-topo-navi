Routing Semantics

Route planning searches a compiled building model for a complete traversable route between two nodes. The result may combine walking within topo maps, transfers between transport landings, and cross-map travel by elevators, escalators, or stairs.

Compiled Routing Model

The compiled building contains one directed navigation graph for each topo map and one transport graph connecting their landing nodes.

  • Each directed atomic path becomes one walking edge.
  • Each bidirectional atomic path becomes two directed walking edges.
  • Each permitted transport ride becomes a directed cross-map edge.
  • A transfer between transports exists only when the two landing nodes are connected by a traversable route on their shared map.

Hard constraints and ride policies have already shaped this model before route planning begins. See Hard Access Constraints.

Route Request

A route request identifies a compiled building, an origin node, a destination node, a building-routing mode, and the requested traversal preferences.

The canonical building ID is part of the URL. Origin, destination, routing mode, traversal preferences, and compilation parameters are supplied in a JSON body. The endpoint requires a platform bearer token unless anonymous access is explicitly enabled for that building.

POST /api/v1/buildings/SkyrimTower/find-route
{
  "startNode": "Lobby::main_entrance",
  "endNode": "OfficeLevel30::reception",
  "routingMode": "partiallyInformed",
  "userParams": {
    "officeAccess": true,
    "timeOfDayInSeconds": 50400
  },
  "traversalPreference": {
    "routePlanningPreference": "MinimizeTime",
    "banTags": ["outdoor"],
    "riskPreference": "conservative"
  }
}

For request construction and endpoint-specific behavior, see the HTTP API reference.

Origin and Destination Resolution

A qualified node identifier has the form MapName::NodeName. Qualified identifiers are strongly recommended because node identifiers are local to their containing maps.

An unqualified node identifier is accepted only when exactly one compiled map contains a node with that identifier.

The request is invalid when the named map does not exist, the named node does not exist in that map, an unqualified name matches no node, or an unqualified name matches nodes in multiple maps.

When the origin and destination are the same node, the result contains no movement.

Same-Map Routing

Same-map requests use the same objective and search strategy as cross-map requests. A direct walking route competes with routes using transport, including leaving and re-entering the map when this improves the requested objective.

The selected route respects path direction, compiled hard access restrictions, banned tags, and uncertain-access policy.

Fully Informed Low-Rise Routing

With routingMode: "fullyInformed", the engine searches individual walking and transport edges in one building-wide network. The requested primary objective and its tie-breakers determine which route is selected.

The resulting total includes:

  1. walking from the origin to the first transport;
  2. cross-map transport travel;
  3. walking transfers between transport landings;
  4. additional transport travel; and
  5. walking from the final transport to the destination.

A slower transport near the origin may therefore be selected instead of a faster transport that requires a long walk.

Route A
100 seconds walking + 1 second express ride + 100 seconds walking
Total: 201 seconds

Route B
1 second walking + 10 second ride + 1 second transfer
+ 10 second ride + 1 second walking
Total: 23 seconds

Fully informed routing selects Route B under MinimizeTime.

MinimizeTransfers, MinimizePhysicalDemands, and MinimizeCustomData are native objectives of this search. For the example above, MinimizeTransfers selects Route A if Route B changes transport lines.

High-Rise Routing

With routingMode: "partiallyInformed", cross-map routing uses a transport-first strategy.

  1. Create a hierarchy containing transport landings and the exact origin and destination.
  2. Compute walking connections from each visited hierarchy node on demand, using the requested objective.
  3. Cache those connections for reuse during this search.
  4. Search walking connections and permitted rides together, using complete-route scores.
  5. Expand the selected connections into the returned route.

Origin, destination, and transfer walking costs participate in route selection, including mandatory intermediate-node dwell. Under MinimizeTime, this mode also selects the 23-second Route B in the example above.

Transport-line changes and custom cost are search objectives. The planner does not first choose time-optimal transport plans and then rerank them. For transfer-aware objectives, the search state includes the previous transport line; walking preserves that line, and boarding the first line counts as zero changes.

Only the best score at a location and previous line is retained. Primary search does not preserve separate labels for every walking history. The first custom-cost definitions are additive, finite, and non-negative, allowing the same search to optimize them directly.

The routingMode value selects a routing strategy independently of the building's physical height or floor count. The API defaults to partiallyInformed; MCP explicitly requests fullyInformed.

Transport Discovery and Selection

Only transports selected by building-includes participate in routing.

A directed ride is available only when:

  • both maps are stations of the transport;
  • departure is permitted at the origin station;
  • arrival is permitted at the destination station;
  • the applicable ride-from policy permits the ordered pair; and
  • the request's uncertain-access policy permits the ride.

An express transport serves only its declared stations. Passing the physical level of an undeclared floor does not make that floor reachable.

Changing between transports requires a traversable atomic-path route between their landing nodes. Serving the same floor does not create a zero-cost transfer. See Transfers Between Transports.

Route-Cost Composition

total route cost =
    walking-path costs
  + transfer-walking costs
  + elevator costs
  + escalator costs
  + stair costs

Atomic-path cost values represent traversal time in seconds. Elevator cost includes estimated waiting and movement time, escalators use their declared fixed travel time, stairs use calculated climbing time, and transfers use the walking cost between landing nodes.

Uncertain access does not add a numeric penalty. The risk preference determines whether an uncertain traversal may participate. Tags and required actions do not add or subtract route cost. Explicit minDwellSeconds adds mandatory dwell at intermediate nodes, excluding the fixed endpoints.

Optimization Guarantees and Search Limits

For valid finite, non-negative costs, native primary search minimizes the requested complete-route ranking when it completes, in either routing mode. Transport travel times remain estimates supplied by the transport model. Returned routes contain no repeated node.

All requests have a shared budget of 50,000 generated labels and 200,000 edge expansions per access-policy search, including on-demand walking connections and any soft-tag refinement. Exhaustion returns HTTP 503 with TRAVERSAL_PREFERENCE_SEARCH_LIMIT; a partial or unverified best-so-far route is not returned.

Situation Current behavior
MinimizeTime Minimum complete traversal time.
MinimizeTransfers Minimum transport-line changes, then complete traversal time.
MinimizePhysicalDemands Minimum complete physical-demand score, then traversal time.
MinimizeCustomData Minimum additive custom cost, then configured transfer/time tie-breakers.
Optional minimizeTag Least exposure within the documented primary tolerance. A zero-exposure primary route needs no further search; otherwise a constrained search runs and may exhaust the shared budget.
Equal-ranked alternatives Deterministic within the implementation; no particular route identity is guaranteed across engine versions.

Tie-Breaking and Determinism

Native primary search compares the objective and tie-breakers listed above. Soft-tag refinement compares exposure, primary score, total time, then canonical route order. See Soft Tag Avoidance for its tolerances.

A strictly cheaper candidate replaces a more expensive candidate. An equal-cost candidate does not replace the route already retained.

Source declaration order, lexical identifier order, and station order are not public tie-breakers. When several routes have equal ranking values, the selected route is unspecified and may change between engine versions.

A fixed request with one uniquely best route produces a stable result. Applications must not depend on the identity of one particular route among exact ties.

No-Route Outcomes

A route may be unavailable because:

  • the origin or destination cannot be resolved;
  • the directed topology does not connect them;
  • an unsatisfied hard constraint removed a required path or ride;
  • a transport station prohibits arrival or departure;
  • a ride-from policy prohibits the required journey;
  • banned tags eliminate every candidate;
  • uncertain access is disallowed and no certain route remains; or
  • required transport transfers are not connected within their floor maps.

The public service distinguishes DESTINATION_HAS_BANNED_TAG, NO_ROUTE_WITH_BAN_TAGS, NO_ROUTE_FOR_USER_PARAMS, and NO_ROUTE_FOUND.

A route request returns either a complete route or a no-route outcome. Partial routes are not returned.

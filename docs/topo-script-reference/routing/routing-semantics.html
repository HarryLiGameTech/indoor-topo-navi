Routing Semantics

Route planning searches a compiled building model for a complete traversable route between two nodes. The result may combine walking within topo maps, transfers between transport landings, and cross-map travel by elevators, escalators, or stairs.

  • Constraints, parameters, and traversal filters

Compiled Routing Model

The compiled building contains one directed navigation graph for each topo map and one transport graph connecting their landing nodes.

  • Each directed atomic path becomes one walking edge.
  • Each bidirectional atomic path becomes two directed walking edges.
  • Each permitted transport ride becomes a directed cross-map edge.
  • A transfer between transports exists only when the two landing nodes are connected by a traversable route on their shared map.

Hard constraints and ride policies have already shaped this model before route planning begins. See Hard Access Constraints.

Route Request

A route request identifies a compiled building, an origin node, a destination node, a building-routing mode, and the requested traversal preferences.

Risk preference, banned tags, route-planning preference, and user parameters are supplied in the request body. The current quick-demo endpoint receives the building name, origin, destination, and isHighRise selector as query parameters.

POST /api/v1/quick-demo-navigation
  ?buildingName=SkyrimTower
  &startNode=Lobby::main_entrance
  &endNode=OfficeLevel30::reception
  &isHighRise=true
{
  "userParams": {
    "officeAccess": true,
    "timeOfDayInSeconds": 50400
  },
  "traversalPreference": {
    "routePlanningPreference": "MinimizeTime",
    "banTags": ["outdoor"],
    "riskPreference": "conservative"
  }
}

For request construction and endpoint-specific behavior, see the Navigation Request Guide.

Origin and Destination Resolution

A qualified node identifier has the form MapName::NodeName. Qualified identifiers are strongly recommended because node identifiers are local to their containing maps.

An unqualified node identifier is accepted only when exactly one compiled map contains a node with that identifier.

The request is invalid when the named map does not exist, the named node does not exist in that map, an unqualified name matches no node, or an unqualified name matches nodes in multiple maps.

When the origin and destination are the same node, the result contains no movement.

Same-Map Routing

When both endpoints belong to the same topo map, the engine searches only that map. Transport services are not considered, even if leaving and re-entering the map could theoretically produce a lower cost.

The selected route minimizes the sum of its atomic-path costs while respecting path direction, hard access restrictions, banned tags, and uncertain-access policy.

This is an exact shortest-path search when all atomic-path costs are non-negative and the compiled topology is valid.

Fully Informed Low-Rise Routing

With isHighRise=false, cross-map routing uses a fully informed hierarchical search. Its hierarchy contains the exact origin, the exact destination, and every transport landing in the building.

For each floor, the engine calculates shortest walking routes between relevant hierarchy nodes. These walking routes are combined with permitted transport rides in one building-wide cost search.

The resulting total includes:

  1. walking from the origin to the first transport;
  2. cross-map transport travel;
  3. walking transfers between transport landings;
  4. additional transport travel; and
  5. walking from the final transport to the destination.

A slower transport near the origin may therefore be selected instead of a faster transport that requires a long walk.

Route A
100 seconds walking + 1 second express ride + 100 seconds walking
Total: 201 seconds

Route B
1 second walking + 10 second ride + 1 second transfer
+ 10 second ride + 1 second walking
Total: 23 seconds

Fully informed routing selects Route B under MinimizeTime.

The current low-rise search always minimizes total traversal cost. MinimizeTransfers and MinimizePhysicalDemands do not change low-rise route selection.

High-Rise Routing

With isHighRise=true, cross-map routing uses a transport-first strategy.

  1. Find transport stations on the origin and destination maps.
  2. Calculate a transport plan for each origin-station and destination-station pairing.
  3. Rank the resulting transport plans according to the requested route preference.
  4. Connect the chosen stations using floor-level walking routes.
  5. Try the next transport plan if a required walking connection is unavailable.

Origin, destination, and transfer walking costs are included in the returned route. Origin and destination walking costs do not participate in the initial transport-plan ranking.

High-rise routing is therefore a transport-prioritized heuristic. It is suitable when transport selection is expected to dominate the journey, but it does not guarantee the globally lowest end-to-end cost.

For each origin-station and destination-station pairing, the candidate set retains only its lowest-cost transport path. Alternative transport paths between the same station pair are not independently ranked by the other preferences.

The isHighRise value selects a routing strategy. It is not checked against the building's physical height or floor count. The quick-demo endpoint defaults it to true.

Transport Discovery and Selection

Only transports selected by building-includes participate in routing.

A directed ride is available only when:

  • both maps are stations of the transport;
  • departure is permitted at the origin station;
  • arrival is permitted at the destination station;
  • the applicable ride-from policy permits the ordered pair; and
  • the request's uncertain-access policy permits the ride.

An express transport serves only its declared stations. Passing the physical level of an undeclared floor does not make that floor reachable.

Changing between transports requires a traversable atomic-path route between their landing nodes. Serving the same floor does not create a zero-cost transfer. See Transfers Between Transports.

Route-Cost Composition

total route cost =
    walking-path costs
  + transfer-walking costs
  + elevator costs
  + escalator costs
  + stair costs

Atomic-path cost values represent traversal time in seconds. Elevator cost includes estimated waiting and movement time, escalators use their declared fixed travel time, stairs use calculated climbing time, and transfers use the walking cost between landing nodes.

Uncertain access does not add a numeric penalty. The risk preference determines whether an uncertain traversal may participate. Tags, required actions, and other application annotations do not add or subtract route cost.

Exact and Heuristic Behavior

Situation Current behavior
Same-map routing Exact minimum atomic-path cost.
Low-rise MinimizeTime Exact end-to-end minimum cost across walking and transport.
Low-rise other preferences The same cost-minimizing behavior as MinimizeTime.
High-rise MinimizeTime Lowest-cost transport plan first; terminal walking is excluded from initial ranking.
High-rise MinimizeTransfers Transport plans are ranked by transport-graph edge count, then transport cost.
High-rise MinimizePhysicalDemands Transport plans are ranked by their transport physical-demand score.
Equal-ranked alternatives No stable public tie-breaking order.

Tie-Breaking and Determinism

A strictly cheaper candidate replaces a more expensive candidate. An equal-cost candidate does not replace the route already retained.

Source declaration order, lexical identifier order, and station order are not public tie-breakers. When several routes have equal ranking values, the selected route is unspecified and may change between engine versions.

A fixed request with one uniquely best route produces a stable result. Applications must not depend on the identity of one particular route among exact ties.

No-Route Outcomes

A route may be unavailable because:

  • the origin or destination cannot be resolved;
  • the directed topology does not connect them;
  • an unsatisfied hard constraint removed a required path or ride;
  • a transport station prohibits arrival or departure;
  • a ride-from policy prohibits the required journey;
  • banned tags eliminate every candidate;
  • uncertain access is disallowed and no certain route remains; or
  • required transport transfers are not connected within their floor maps.

The public service distinguishes DESTINATION_HAS_BANNED_TAG, NO_ROUTE_WITH_BAN_TAGS, NO_ROUTE_FOR_USER_PARAMS, and NO_ROUTE_FOUND.

A route request returns either a complete route or a no-route outcome. Partial routes are not returned.

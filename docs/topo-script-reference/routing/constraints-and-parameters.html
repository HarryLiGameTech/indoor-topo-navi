Constraints, Parameters, and Traversal Filters

TopoNavi separates access conditions that shape the compiled building from request-time controls that filter or rank routes through that building.

Compilation Inputs and Route Inputs

User parameters are compilation inputs. They determine the user's access and capability context while the building is compiled:

{
  "userParams": {
    "officeAccess": true,
    "carryingWeight": 20,
    "timeOfDayInSeconds": 50400
  }
}

Risk preference, banned tags, and route-planning preference are request-time traversal controls:

{
  "traversalPreference": {
    "routePlanningPreference": "MinimizeTime",
    "banTags": ["outdoor", "rain_exposed"],
    "riskPreference": "conservative"
  }
}

Both groups are supplied in the navigation request body. For the full request format, see the Navigation Request Guide.

User parameters form part of the compiled-building cache identity. Changing them requires a matching compiled model. Traversal controls do not modify the compiled graph and may vary between route requests.

Hard Access Constraints

A failed requires condition is a hard prohibition. Depending on its attachment point, it may remove an atomic path, prohibit arrival at a station, prohibit departure from a station, prohibit both arrival and departure, or prohibit a directed transport ride.

atomic-path [public_hall -> staff_corridor] {
  cost = 4
} requires StaffAccess

When StaffAccess is false, the directed path is absent from the usable compiled topology.

Hard constraints are evaluated during compilation. The route planner consumes their compiled effects and does not re-evaluate their expressions. See Compilation Time and Routing Time.

Uncertain Access

A subject-to condition describes a traversal that may be unavailable but is not a definite prohibition.

atomic-path [public_hall -> rooftop_garden] {
  cost = 12
} subject-to RooftopOpen
  because "The rooftop may close during severe weather."

If RooftopOpen is satisfied, the path is treated as ordinarily available.

If it is unsatisfied, the path remains in the compiled model, conservative searches exclude it, permissive searches may select it, and a selected route exposes its uncertainty reason.

Repeated failed uncertainty conditions of the same type are consolidated in route-level disclosure. A requires condition and a subject-to condition cannot be attached to the same element.

Risk Preferences

conservative

The engine first searches without failed subject-to traversals. If a certain route exists, that route is returned.

If no certain route exists, the engine retries with uncertain traversals enabled and reports permissive as the applied risk preference. Conservative routing therefore prefers a certain route but returns an uncertain route rather than failing when it is the only available option.

permissive

The engine calculates the best route excluding failed uncertain access and the best route allowing it. The uncertain route is selected only when it meaningfully improves the primary route objective:

Primary preference Required improvement
MinimizeTime At least 15 seconds faster.
MinimizeTransfers At least one fewer non-walking segment.
MinimizePhysicalDemands At least a 10% lower physical-demand score.

If no certain route exists, the uncertain route is returned.

aggressive

All uncertain traversals are admitted into the search. The best resulting route is returned without comparison against a certain-only route.

permissive and aggressive do not assert that access is lawful, safe, or physically available. Uncertainty descriptions originate from the map author and may be inaccurate or outdated.

Banned Tags

banTags is a request-scoped hard filter over node and atomic-path tags.

{
  "traversalPreference": {
    "banTags": ["outdoor", "rain_exposed"]
  }
}

A route cannot traverse an atomic path containing a banned tag or enter a node containing a banned tag. Node and path tags are evaluated independently; a node tag is not automatically inherited by its incident paths.

Endpoint behavior is:

  • A source node may contain a banned tag because the user is already there.
  • Outgoing paths from that source are still checked.
  • A destination containing a banned tag produces DESTINATION_HAS_BANNED_TAG.
  • An intermediate node containing a banned tag cannot be entered.

Tag matching is exact and case-sensitive. If tag filtering leaves no route, the service returns NO_ROUTE_WITH_BAN_TAGS.

Transport rides do not carry traversable tags of their own. Tags on transport landing nodes can prevent entry into those landings.

For tag-authoring conventions, see the TopoScript Tagging Guide. For request-body usage, see the Navigation Request Guide.

Required Actions and Other Annotations

Atomic-path annotations are preserved on returned walking segments. The annotation keys requiredActions, required_actions, and action_required are recognized as required-action lists.

atomic-path [public_hall -> controlled_door] {
  cost = 5,
  requiredActions = ["tap_access_card", "open_door"]
}

Required actions are reported to the consuming application but do not affect route eligibility, cost, or ranking. The application is responsible for presenting or handling them.

Other custom path annotations are not interpreted as routing rules unless explicitly documented.

Compiled and Runtime Outputs

TopoNavi Engine compiles a TopoScript project into a building model and uses that model to produce an ordered route plan. Applications commonly receive a JSON representation of the route plan through the TopoNavi web service.

This article defines the relationship between TopoScript declarations and the current consumer-visible output. HTTP status codes, cache metadata, and service-specific response envelopes are API concerns rather than TopoScript language semantics.

Output Boundary

The compiler's internal result contains per-map navigation graphs, a transport graph, map ordering, spatial hints, and compiler metadata. These internal Scala objects are not a portable serialization format and are not a public JSON contract.

The supported consumer-facing representation is a route projected into ordered structured steps and waypoint records. REST, MCP, editor, and agent integrations may wrap or transform that representation. Such envelopes do not change the meaning of a node, path, topo map, or transport.

Compiled-Building Views

A compiled building contains the map graphs and connecting transport graph described by Relationship to the Compiled Building. The current web service provides convenience views for:

  • available maps;
  • available nodes, with optional node attributes;
  • compiled directed walking edges;
  • compiled elevators and their stations;
  • one node's attributes; and
  • nodes reachable near a supplied node.

These are web-service projections of the compiled model, not additional TopoScript entities. Consumers must not serialize or persist the engine's internal graph objects as though they were a language-defined interchange format.

Successful Route Response

The current quick-demo REST endpoint returns the following top-level fields after a successful route request:

Field Meaning
status "success" for a successful web request.
path A human-readable rendering of the route. It is for display and inspection, not machine parsing.
steps The ordered structured route steps defined below.
appliedTraversalPreference The applied route-planning preference, banned tags, and risk preference. See Request-Body Controls.
riskSummary Present only when the selected route uses uncertain access.
deprecations Machine-readable notices for response fields that consumers should replace.
filesLoaded, cacheKey, fromCache Quick-demo service metadata. These fields do not describe the route or the TopoScript language.

The structured response does not currently contain a top-level numeric total. A consumer can obtain the route's total traversal time by summing costSeconds across all steps.

Step Order and Types

steps is in traversal order. Each step number is one-based and increases contiguously.

type Meaning Source relationship
Walk One or more consecutive walking edges on one map. Generated from traversed atomic-path declarations.
WalkStraight A walking group recognized as part of one declared straight line. Generated when traversed atomic paths match a linear-path.
Transport An elevator or escalator ride between maps. Generated from a selected transport ride.
Climbing A stair traversal between maps. Generated from a selected stairs transport.

Consecutive walking edges on the same map are grouped into one Walk step unless spatial hints split them into WalkStraight steps. Every non-walking route edge becomes its own transport or climbing step.

Walking-Step Fields

Field Presence Meaning
step, type Always Sequence number and Walk or WalkStraight.
graph Always The identifier of the containing topo map.
from, to Always Human-readable endpoint strings assembled from node identifiers and descriptions. Prefer waypoints for machine use.
waypoints Always Structured, ordered node records traversed by the step.
namedWaypoints Currently present Legacy human-readable strings. This field is marked for deprecation; use waypoints.
costSeconds Always The sum of the traversed atomic-path costs, in seconds.
tags Always The distinct, sorted tags collected from the step's atomic paths.
requiredActions, requiredActionEvents Always Application-facing actions collected from the traversed paths, plus their exact edge locations.
uncertainAccess Conditional Present when the step uses one or more uncertain paths.
turnDirection, turnAtNode Conditional on WalkStraight A resolved turn hint for entering this straight segment.

Transport and Climbing Step Fields

Field Meaning
step, type The sequence number and either Transport or Climbing.
description A human-readable sentence identifying the transport and endpoint maps, such as Take OfficeExpress from Lobby to OfficeLevel30.
fromGraph, toGraph The identifiers of the departure and arrival maps.
waypoints The ordered departure and arrival landing nodes.
costSeconds The calculated ride or climbing time in seconds. Its calculation depends on the elevator, escalator, or stair model.
tags, requiredActions, requiredActionEvents Present as arrays. Current transport rides do not contribute transport-level tags or required actions.
uncertainAccess Present when the selected ride uses uncertain station access.

Walking to a landing, walking between two landing nodes during a transfer, and walking away from a landing are ordinary walking steps. Transport entry, ride, transfer, and exit are therefore not encoded as four artificial event types: the ordered walking and transport steps preserve the actual modeled movement.

Waypoints, Identifiers, and Descriptions

Each waypoint contains nodeId and graph. Together they identify the source node as graph::nodeId, matching the qualified-name form used by route requests and transport stations.

The structured waypoint projection also includes the recognized node properties: description, shop and facility names and categories, positions and throughput data, tags, narration, refVisualUrl, and beaconId. Missing optional values are serialized as null; missing node tags are serialized as an empty array.

isIntermediate states whether a waypoint lies between the first and last waypoint of that step. isTrivial identifies a node that normally needs no standalone presentation; an explicit isTrivial node property overrides the default classification.

Generated internal routing nodes are omitted from the waypoint projection. Consumers should use structured waypoint fields for labels and localized narration rather than parsing from, to, path, or a transport step's description.

Cost, Duration, and Distance

costSeconds is a floating-point traversal-time value in seconds. The route cost is the sum of walking, transfer-walking, elevator, escalator, and stair time described by Route-Cost Composition.

The current route result does not expose geometric distance. Node coordinates, estimated coordinates, and arbitrary application annotations must not be interpreted as a route-distance field.

Required Actions

requiredActions is a de-duplicated list of actions collected from the step's path annotations. requiredActionEvents preserves where each action occurs:

{
  "action": "tap_access_card",
  "from": "public_hall",
  "to": "controlled_door",
  "graph": "OfficeLevel30"
}

Actions inform the consuming application. They do not change route eligibility, traversal cost, or ranking. The recognized source keys and their behavior are defined in Required Actions and Other Annotations.

Uncertain Access and Access Failures

A returned step that uses uncertain access contains:

"uncertainAccess": {
  "uncertaintyReasons": [
    {
      "type": "CardAccess",
      "reason": "The floor button may require a card."
    }
  ],
  "message": "This segment may require additional access and may not always be available."
}

The successful response also contains a top-level riskSummary with routeNotNecessarilyAvailable, the applied risk preference, aggregated uncertainty reasons, and a disclaimer.

A failed hard requires condition removes the affected path, station permission, or ride from the compiled routing model. It is not emitted as a warning on an otherwise successful route. If the remaining model has no complete route, the request produces a no-route response.

Spatial and Turn Hints

A linear-path can divide a walking route into WalkStraight steps. It does not create connectivity or add cost.

When a matching directional-arrow exists at the boundary between straight segments, the later segment may contain:

{
  "type": "WalkStraight",
  "turnDirection": "LEFT",
  "turnAtNode": "atrium_junction"
}

turnDirection is resolved for the route's actual direction of travel. turnAtNode is the arrow's anchor node, where the turn applies. When no matching hint exists, both fields are absent.

Empty, Failed, and No-Route Results

Origin equals destination
The route is successful, steps is empty, and the human-readable path states that no movement is required.
No complete route
The service returns an error response rather than a partial route. Common codes include NO_ROUTE_FOUND, NO_ROUTE_FOR_USER_PARAMS, and NO_ROUTE_WITH_BAN_TAGS.
Banned destination
The service returns DESTINATION_HAS_BANNED_TAG with the qualified node identifier and conflicting tags.
Invalid project
Compilation fails before routing. See Validation and Error Reporting.

A route response is complete or absent. The current engine does not return a best-effort prefix ending at the point where navigation became impossible. See No-Route Outcomes.

Ordering and Optionality

  • Steps and waypoints are ordered by traversal.
  • Step numbers are one-based and contiguous.
  • Path tags are distinct and sorted.
  • Required actions are de-duplicated while preserving their first encountered order.
  • turnDirection, turnAtNode, uncertainAccess, and top-level riskSummary are omitted when inapplicable.
  • Equal-ranked alternative routes have no stable selection order. See Tie-Breaking and Determinism.

Serialization and Compatibility

Structured output uses JSON objects, arrays, strings, numbers, Booleans, and null. Applications should consume documented structured fields and tolerate the addition of new optional fields.

The exact text of path, from, to, transport description, disclaimers, and error messages is human-readable output rather than a stable identifier. Applications must not branch on that wording.

The response's deprecations array currently marks steps[].namedWaypoints as scheduled for replacement by steps[].waypoints. Consumers should migrate to the structured field.

REST fields such as HTTP status, cache state, and loaded-file count belong to the web adapter. An MCP server, editor, or agent may use a different envelope while preserving the route-step meanings defined here.

Topo Maps

A topo-map instance describes the local navigation topology of one certain floor. It contains the floor's nodes, atomic paths, and optional declarations used to explain local movement.

A topo map describes connectivity rather than a metric floor plan. Movement between topo maps belongs to a transport declaration, not to an atomic path.

Responsibilities and Boundaries

One topo-map instance must model one certain floor. A topo map must not combine nodes from different floors merely because those nodes can be connected in one graph. A reusable topo-map source may define a standard-floor template, but every resulting instance still represents one particular floor.

It is algorithmically possible to place every node of a building into one super-map, but doing so is extremely discouraged. A super-map:

  • erases the semantic boundary between movement on a floor and movement between floors;
  • bypasses the transport model used for elevators, escalators, and stairs;
  • makes floor-specific management domains, access rules, route explanations, and updates harder to express and audit;
  • prevents effective reuse of standard-floor topology; and
  • increases the impact of a local mapping mistake by placing unrelated floors in the same graph.

These are modeling and maintainability boundaries, not graph-theory limitations.

Declaration

topo-map MallLevel5() {
  let params = {}

  topo-node atrium
  topo-node east_lift_lobby

  atomic-path [atrium <-> east_lift_lobby] {
    cost = 12.0
  }
}

The map name is an identifier. For a directly included map, the name in the declaration, the source filename, and the submap name in building-includes should agree exactly, including case.

The header may syntactically contain a parameter list, but map-instance argument passing is not currently defined. Authors should use an empty header parameter list and place local calculated values in the map body.

The params Record

Every compiled topo map must define a local params record. Use an empty record when the map has no recognized parameters:

let params = {}

The optional recognized field permResident is an Int describing the floor's permanent resident population:

let params: {permResident: Int} = {
  permResident = 180
}

When elevator-demand modeling needs this value and it is omitted, the TopoNavi Engine uses 1. Additional fields may be used by local expressions, but the engine does not assign them standard map-level routing semantics.

Management-Domain Override

A topo map may override the management domain assigned by building-includes:

topo-map TradingFloor() override-managed-by TradingDomain {
  let params = {}
}

The effective-domain precedence is documented in Management-Domain Attachment.

Intra-Map Movement

Nodes and atomic paths describe movement within the map. An atomic path must therefore reference two nodes declared in the same topo map.

An elevator landing, stair landing, or escalator landing is still an ordinary node in its floor map. A transport station later refers to that node and provides the cross-map connection.

Map Tags

The current topo-map declaration has no map-level annotation record and therefore no map-level tags field. Tags may be attached to nodes and atomic paths. See TopoScript Tagging Guide for the canonical vocabulary and placement rules.

Disconnected and Invalid Topology

A disconnected node or disconnected component is permitted, but no intra-map route can cross the gap. This can intentionally represent an unmapped or currently unreachable area; otherwise it usually indicates a missing atomic path.

Node identifiers must be unique within a topo map. Duplicate declarations make references ambiguous and are invalid authoring practice, although the current compiler does not consistently diagnose every duplicate.

A path that names an undeclared node fails during elaboration. Negative path costs are invalid because routing requires non-negative weights, but the current compiler checks only that cost is numeric; explicit non-negative validation is not yet implemented.

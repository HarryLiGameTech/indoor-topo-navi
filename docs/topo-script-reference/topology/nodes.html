Nodes

A node is a named topological entity representing one unambiguous, physically bounded area of a venue.

Nodes belong to one topo map and therefore to one certain floor.

Physical Semantics

A node may represent a destination area, entrance area, doorway area, junction area, corridor-corner area, transport-landing area, decision area, or another navigation-relevant region.

The physical areas represented by any two distinct nodes must not overlap. Under Region Connection Calculus topology, their relationship must be one of:

  • Disconnected (DC): the two areas do not share any physical point.
  • Externally connected (EC): the boundaries of the two areas touch, but their interiors do not intersect.

Distinct nodes must therefore not partially overlap, represent equal physical areas, or contain one another. If a physical region would otherwise be represented by overlapping nodes, the author must partition it into non-overlapping node areas.

Recommended Granularity

As a mapping guideline, a node should be small enough that the longest reasonable walking line across its area takes no more than five seconds. This is the node's longest “diagonal” in walking-time terms; it does not require metric coordinates or a geometrically rectangular area.

If crossing the represented area can take longer than five seconds, consider partitioning it into finer, non-overlapping nodes connected by atomic paths. This threshold is an authoring recommendation and is not enforced by the compiler.

Syntax

topo-node east_lift_lobby

A node may carry an annotation record:

topo-node visitor_reception {
  description = "Visitor reception desk",
  facilityName = "Reception",
  tags = ["staffed"],
  narration = "explicit"
}

The node identifier is local to its containing topo map. Local paths and navigation-hint declarations use the simple name. A transport refers to the node with a qualified name such as MallLevel5::east_lift_lobby.

Supported Properties

The annotation record is optional. Integer, floating-point, Boolean, string, and list values are preserved as compiled node attributes and may be exposed to applications.

The TopoNavi Engine's structured route output recognizes and exposes these node fields when present:

  • description
  • shopName or shop_name
  • facilityName or facility_name
  • shopCategory or shop_category
  • facilityCategory or facility_category
  • positions
  • observedThroughput or observed_throughput
  • maxThroughput or max_throughput
  • tags
  • narration
  • refVisualUrl or ref_visual_url
  • beaconId or beacon_id
  • isTrivial or is_trivial

Other attributes are application-defined. They are retained in the compiled node data, but TopoScript does not prescribe how every application must interpret them.

Tags

Store node tags as a list of canonical strings in tags. For placement rules and the supported vocabulary, read the TopoScript Tagging Guide.

Connectivity

A node may participate in zero or more atomic paths and may be referenced by one or more transport stations. Declaring a node alone does not make it reachable.

Valid Partition Example

A long concourse containing a junction and two lift lobbies should be partitioned into distinct regions:

topo-node west_lift_lobby
topo-node central_junction
topo-node east_lift_lobby

atomic-path [west_lift_lobby <-> central_junction] {
  cost = 18.0
}

atomic-path [central_junction <-> east_lift_lobby] {
  cost = 16.0
}

Invalid Overlap Example

Do not model the same physical junction once as part of a corridor node and again as a separate junction node. The two represented areas would overlap. Partition the corridor at the junction and connect the resulting nodes instead.

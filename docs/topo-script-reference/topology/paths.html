Paths and Local Movement

An atomic path declares direct, traversable connectivity between two nodes in the same topo map. Atomic paths are the weighted edges used for intra-floor route calculation.

Atomicity

An atomic path must connect exactly two nodes without physically crossing another intermediate node. If traveling from one represented place to another necessarily makes a person pass through a third node, the connection must be split.

For nodes A, B, and C encountered in that order, declare:

atomic-path [A <-> B] {
  cost = 8.0
}

atomic-path [B <-> C] {
  cost = 6.0
}

Do not also declare A <-> C when every physical traversal from A to C necessarily passes through B. Such an edge would hide a real decision or passage point from the topology.

Syntax and Direction

A directed path permits traversal only from the left node to the right node:

atomic-path [entry_gate -> paid_concourse] {
  cost = 4.0
}

A bidirectional path creates traversal in both directions with the same cost and attributes:

atomic-path [north_corridor <-> central_junction] {
  cost = 9.0
}

If the directions have different costs or annotations, declare two directed atomic paths:

atomic-path [lower_ramp -> upper_ramp] {
  cost = 15.0,
  tags = ["up_slope"]
}

atomic-path [upper_ramp -> lower_ramp] {
  cost = 10.0,
  tags = ["down_slope"]
}

Path Cost

Every atomic path must contain a numeric cost field:

atomic-path [atrium -> information_desk] {
  cost = 7.5
}

The value may be an Int or Float and must be non-negative. The routing algorithm combines path costs to compare candidate routes.

cost is the only atomic-path weight required by the TopoNavi Engine. TopoScript does not require separate distance or time fields. Applications may add such annotations, but their meaning and use are application-defined.

Path Properties

Fields other than cost are annotations. Primitive values and lists are preserved in the compiled path and may be exposed verbatim through application responses.

atomic-path [shopfront -> outdoor_terrace] {
  cost = 5.0,
  tags = ["door", "outdoor", "rain_exposed"],
  doorLabel = "Terrace Door T5"
}

The TopoNavi Engine recognizes tags for traversal filtering and route metadata. The meaning of custom fields such as doorLabel belongs to the consuming application.

Tags

Store path tags as a list of canonical strings in tags. For placement rules and the supported vocabulary, read the TopoScript Tagging Guide.

Uncertain Access

subject-to records that a path remains physically present but may be unavailable:

atomic-path [public_gallery <-> roof_terrace] {
  cost = 8.0
}
subject-to InGoodWeather because "The terrace may close in severe weather."

The path remains in the compiled topology. Full syntax and examples are provided in Representing Uncertain Access. Routing-time selection, propagation, and disclosure belong to Uncertain Access and Risk Handling.

Straight-Line Hints

A linear-path lists at least three local nodes in their physical order along one straight corridor or other straight walking line:

linear-path [west_lift_lobby, atrium_junction, east_lift_lobby]

This declaration does not create connectivity. The required atomic paths must still be declared separately. The hint allows route output to group matching walking edges into straight-line legs.

Turn Hints

A directional-arrow states where a target node lies relative to a facing direction established at an anchor node:

directional-arrow [ANCHOR -> REFERENCE] TARGET DIRECTION
ANCHOR
The node where the turn or directional instruction applies.
REFERENCE
The node used to establish which way the traveler is facing while at the anchor.
TARGET
The node whose position is being described relative to that facing direction.
directional-arrow [atrium_junction -> west_lift_lobby] food_court_entrance LEFT

In this example, the anchor is atrium_junction. While standing there and facing toward the reference node west_lift_lobby, the target food_court_entrance is on the traveler's left.

With ->, a traveler at the anchor faces toward the reference node. With <-, the traveler at the anchor faces away from the reference node:

directional-arrow [atrium_junction <- west_lift_lobby] east_exit FRONT_RIGHT

The supported relative directions are FRONT, FRONT_RIGHT, RIGHT, REAR_RIGHT, REAR, REAR_LEFT, LEFT, and FRONT_LEFT.

A directional arrow neither creates a path nor changes route cost. When it matches a boundary between straight-line legs, structured route output may expose the resolved turn direction and the node at which the turn occurs.

Validation

  • Both endpoints must resolve to nodes in the containing topo map.
  • cost must be an Int or Float and must not be negative.
  • A linear-path must contain at least three declared nodes.
  • Every node named by a directional arrow must exist in the containing topo map.
  • A direction name in a directional arrow must be one of the eight supported values.

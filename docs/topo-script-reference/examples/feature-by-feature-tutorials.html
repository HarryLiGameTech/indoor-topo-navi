Feature-by-Feature Tutorials

Status: Draft

Purpose

This tutorial series introduces TopoScript one feature at a time. Each tutorial uses a fictional but realistic indoor venue, presents valid source code, and contrasts it with code that is invalid or misleading.

Examples are classified as follows:

Compilation-invalid
The TopoNavi Engine rejects the source or supplied compilation parameters.
Modeling-invalid
The source may compile, but it does not truthfully represent the physical venue.
Unsupported assumption
The source compiles, but the author expects behavior that the TopoNavi Engine does not provide.

All venues and operational details in these tutorials are synthetic. File extensions are shown for clarity; the compiler also supports the documented extensionless source names.

1. Creating a Minimal Building Project

Scenario: A neighborhood library has one public floor, one street entrance, and one reception area.

Real-place analogy: The building configuration resembles the directory at the entrance: it identifies the mapped areas that belong to this venue. The topo-map then describes movement within one of those areas.

Valid example

configuration.tcfg

building-includes {
  submap LibraryGroundFloor
}

LibraryGroundFloor.tmap

topo-map LibraryGroundFloor() {
  let params = { permResident = 0 }

  topo-node street_entrance
  topo-node reception

  atomic-path [street_entrance <-> reception] {
    cost = 12.0
  }
}

The project compiles one map containing two nodes and one path in each direction. A route can be requested between LibraryGroundFloor::street_entrance and LibraryGroundFloor::reception.

Invalid example: referenced source is absent

configuration.tcfg

building-includes {
  submap LibraryGroundFloor
}

If neither LibraryGroundFloor.tmap nor an extensionless LibraryGroundFloor source is supplied, the project is incomplete. The current compiler reports a missing-map warning and cannot produce the intended library graph.

Related reference: Source-File and Project Boundaries

2. Modeling Maps and Nodes

Scenario: A clinic floor contains a reception area, a waiting area, a corridor corner, and the area immediately outside an examination room.

Real-place analogy: Each node is a bounded area where a visitor can arrive, depart, enter another space, or make a navigation decision. It is not a pin placed somewhere inside a larger overlapping node.

Valid example

ClinicFloor.tmap

topo-map ClinicFloor() {
  let params = { permResident = 18 }

  topo-node reception_area
  topo-node waiting_area
  topo-node corridor_corner_NE
  topo-node exam_room_3_outside

  atomic-path [reception_area <-> waiting_area] { cost = 6.0 }
  atomic-path [waiting_area <-> corridor_corner_NE] { cost = 8.0 }
  atomic-path [corridor_corner_NE <-> exam_room_3_outside] { cost = 5.0 }
}

Each name denotes a distinct, non-overlapping physical area. Neighboring areas may touch at their boundaries, but their interiors do not intersect.

Invalid example: overlapping node meanings

ClinicFloor.tmap

topo-map ClinicFloor() {
  let params = { permResident = 18 }

  // Intended to represent the entire corridor, including its northeast corner.
  topo-node entire_corridor

  // Intended to represent an area contained inside entire_corridor.
  topo-node corridor_corner_NE

  atomic-path [entire_corridor <-> corridor_corner_NE] { cost = 1.0 }
}

Classification: Modeling-invalid. The compiler has no venue geometry with which to detect the overlap. The author must partition the corridor into non-overlapping node areas instead.

Related reference: Node

3. Connecting Nodes with Atomic Paths

Scenario: A museum corridor leads from the public entrance past an information desk to an exhibition entrance.

Real-place analogy: A visitor walking to the exhibition necessarily crosses the information-desk area. The corridor must therefore be split at that navigation-relevant area.

Valid example

topo-node public_entrance
topo-node information_desk
topo-node exhibition_entrance

atomic-path [public_entrance <-> information_desk] {
  cost = 9.0
}

atomic-path [information_desk <-> exhibition_entrance] {
  cost = 14.0
}

The route from the entrance to the exhibition passes through information_desk.

Invalid example: skipping an intermediate node

atomic-path [public_entrance <-> exhibition_entrance] {
  cost = 23.0
}

Classification: Modeling-invalid if this physical passage necessarily crosses the information-desk node. The direct path is valid only if it represents a genuinely separate traversal that bypasses the desk.

Invalid example: missing path cost

atomic-path [information_desk <-> exhibition_entrance] {
  description = "Main exhibition corridor"
}

Classification: Compilation-invalid. Every atomic path must contain a numeric cost.

Related reference: Atomic Path

4. Directed and Bidirectional Movement

Scenario: A supermarket has a one-way entrance gate, a separate exit gate, and ordinary two-way aisles.

Real-place analogy: Direction describes how people may actually move. The entrance gate admits customers but does not provide the return journey, while an aisle permits travel both ways.

Valid example

topo-node street_entrance
topo-node entrance_lobby
topo-node aisle_junction
topo-node checkout_hall

atomic-path [street_entrance -> entrance_lobby] { cost = 4.0 }
atomic-path [entrance_lobby <-> aisle_junction] { cost = 10.0 }
atomic-path [aisle_junction <-> checkout_hall] { cost = 12.0 }

The first path permits entry only. Each bidirectional declaration produces traversal in both directions.

Invalid example: false reverse access

// Incorrect if the physical gate permits entry only.
atomic-path [street_entrance <-> entrance_lobby] { cost = 4.0 }

Classification: Modeling-invalid. This declaration creates a return traversal that the venue does not permit.

Related reference: Atomic Path

5. Adding Custom Node and Path Annotations

Scenario: A shopping center application displays tenant descriptions and distinguishes indoor and covered outdoor passages.

Real-place analogy: An annotation resembles information attached to an entry in a venue directory. TopoScript can carry that information without deciding how every application must display or interpret it.

Valid example

topo-node bakery_entrance {
  description = "Entrance beside the central atrium",
  tenantCategory = "food_and_drink",
  directoryAliases = ["Bakery", "Cafe"]
}

topo-node atrium_walkway

atomic-path [atrium_walkway <-> bakery_entrance] {
  cost = 7.0,
  passageType = "indoor"
}

The custom values are preserved as structured node and path attributes. A consuming application may expose them as JSON-compatible strings and lists.

Invalid example: expecting automatic business-hours enforcement

topo-node pharmacy_entrance {
  businessHours = "09:00-18:00",
  openNow = false
}

topo-node mall_corridor

atomic-path [mall_corridor <-> pharmacy_entrance] {
  cost = 5.0
}

Classification: Unsupported assumption. These custom annotations do not automatically remove the pharmacy path from the compiled topology. Business-hours behavior must be implemented by the application or expressed through supported compilation parameters and constraints.

Related reference: Stability Boundaries

6. Using Values and Expressions

Scenario: Several airport-concourse paths include the same expected delay for passing through a fire door.

Real-place analogy: A shared value works like using one agreed door-delay estimate throughout a facilities plan instead of manually repeating the calculation.

Valid example

let fireDoorDelay = 2.0
let shortCorridorTime = 8.0

topo-node gate_lounge
topo-node fire_door_landing
topo-node transfer_corridor

atomic-path [gate_lounge <-> fire_door_landing] {
  cost = shortCorridorTime + fireDoorDelay
}

atomic-path [fire_door_landing <-> transfer_corridor] {
  cost = 12.0 + fireDoorDelay
}

The expressions are evaluated during compilation, producing numeric costs of 10.0 and 14.0.

Invalid example: mixing numeric types

let corridorSeconds = 8

atomic-path [gate_lounge <-> fire_door_landing] {
  cost = corridorSeconds + 2.0
}

Classification: Compilation-invalid. General expressions do not implicitly convert between Int and Float.

Invalid example: parsed but unsupported operator

let halfTransferTime = 30.0 / 2.0

Classification: Compilation-invalid. Division appears in the current grammar but is not implemented by the surface-language evaluator.

Invalid example: unknown value

atomic-path [gate_lounge <-> fire_door_landing] {
  cost = measuredDoorDelay + 8.0
}

Classification: Compilation-invalid because measuredDoorDelay is not defined in a visible scope.

Related reference: Literals, Expressions, Operators, and Evaluation

7. Parameters and Access Constraints

Scenario: An office has a public reception route and a shorter staff-only entrance to its records room.

Real-place analogy: The physical corridor is unchanged, but the compiled accessible topology depends on whether the intended user has staff access.

Valid example

configuration.tcfg

building-includes {
  submap OfficeFloor
}

root

root OfficeBuilding(hasStaffAccess: Bool) {
  constraint StaffOnly {
    require hasStaffAccess
  }
}

OfficeFloor.tmap

topo-map OfficeFloor() {
  let params = { permResident = 45 }

  topo-node reception
  topo-node public_corridor
  topo-node staff_door
  topo-node records_room

  atomic-path [reception <-> public_corridor] { cost = 8.0 }
  atomic-path [public_corridor <-> records_room] { cost = 20.0 }
  atomic-path [reception <-> staff_door] { cost = 5.0 }
  atomic-path [staff_door <-> records_room] { cost = 4.0 }
    requires StaffOnly
}

Compiling with the following parameter makes the staff path available:

{
  "userParams": {
    "hasStaffAccess": true
  }
}

Compiling with false excludes the constrained path. Changing the parameter requires another compilation.

Invalid example: required parameter omitted

{
  "userParams": {}
}

Classification: Compilation-invalid because hasStaffAccess has no supplied value.

Invalid example: parameter has the wrong type

{
  "userParams": {
    "hasStaffAccess": "yes"
  }
}

Classification: Compilation-invalid. The constraint requires a Boolean predicate, but this value evaluates as a String.

Related reference: Parameters and Constraints

8. Reusing a Standard Floor Map

Scenario: Hotel guest floors 8, 9, and 10 have the same corridor and room-layout topology.

Real-place analogy: The floors were built from the same architectural plan, but each remains a separately named place that an elevator can serve.

Valid example

configuration.tcfg

building-includes {
  submap Floor8 using StandardGuestFloor
  submap Floor9 using StandardGuestFloor
  submap Floor10 using StandardGuestFloor
}

StandardGuestFloor.tmap

topo-map StandardGuestFloor() {
  let params = { permResident = 72 }

  topo-node elevator_lobby
  topo-node corridor_junction
  topo-node room_01_outside

  atomic-path [elevator_lobby <-> corridor_junction] { cost = 9.0 }
  atomic-path [corridor_junction <-> room_01_outside] { cost = 11.0 }
}

The compiled building contains distinct maps named Floor8, Floor9, and Floor10, each reusing the standard topology.

Invalid example: unknown base map

configuration.tcfg

building-includes {
  submap Floor8 using StandardGuestFlorr
}

Classification: Invalid project. If no source named StandardGuestFlorr.tmap or StandardGuestFlorr exists, the compiler reports that the base map is missing and cannot construct the intended floor instance.

Related reference: Map

9. Connecting Floors with an Elevator

Scenario: A three-level office building has one two-car elevator bank serving the lobby and two office floors.

Real-place analogy: A map node represents the landing area. An elevator station represents this elevator bank's use of that landing.

Valid example

configuration.tcfg

building-includes {
  submap Lobby
  submap Office2
  submap Office3
  vehicle MainElevator
}

Each referenced map contains its own landing node.

Lobby.tmap

topo-map Lobby() {
  let params = { permResident = 6 }
  topo-node main_elevator_landing
}

Office2.tmap

topo-map Office2() {
  let params = { permResident = 80 }
  topo-node main_elevator_landing
}

Office3.tmap

topo-map Office3() {
  let params = { permResident = 75 }
  topo-node main_elevator_landing
}

MainElevator.ttr

transport MainElevator is Elevator {
  let params = {
    maxVelocity = 2.0,
    acceleration = 0.8,
    duty = 1000,
    capacity = 13,
    carAmount = 2
  }

  let displayName = "Main elevator bank"

  station Lobby at Lobby::main_elevator_landing {
    location = 0.0,
    departureRate = 0.10
  }

  station Floor2 at Office2::main_elevator_landing {
    location = 4.2,
    departureRate = 0.10
  }

  station Floor3 at Office3::main_elevator_landing {
    location = 8.4,
    departureRate = 0.10
  }
}

The stations connect three qualified map nodes through one elevator. The transport parameters are used by the TopoNavi Engine when estimating elevator travel.

Invalid example: incomplete station data

station Floor2 at Office2::main_elevator_landing {
  location = 4.2
}

Classification: Compilation-invalid. An elevator station requires a floating-point departureRate.

Invalid example: unknown landing node

station Floor3 at Office3::service_elevator_landing {
  location = 8.4,
  departureRate = 0.10
}

Classification: Compilation-invalid if service_elevator_landing is not declared by Office3.

Invalid example: no possible inter-map ride

transport MainElevator is Elevator {
  let params = { maxVelocity = 2.0 }

  station Lobby at Lobby::main_elevator_landing {
    location = 0.0,
    departureRate = 0.10
  }
}

Classification: Modeling-invalid. One station cannot provide travel between maps; an operational elevator model requires at least two station maps.

Related reference: Transport and Station

10. Modeling Stairs and Escalators

Scenario: A railway concourse has a staircase between three levels and an escalator between the lower concourse and platform level.

Real-place analogy: Stair stations identify landings along a continuous stair run. An escalator is modeled as one timed connection between exactly two station maps.

configuration.tcfg

building-includes {
  submap StreetLevel
  submap LowerConcourse
  submap PlatformLevel
  vehicle ConcourseStairs
  vehicle PlatformEscalator
}

The three topo maps declare the corresponding landing nodes.

StreetLevel.tmap

topo-map StreetLevel() {
  let params = { permResident = 0 }
  topo-node stair_landing
  topo-node escalator_landing
}

LowerConcourse.tmap

topo-map LowerConcourse() {
  let params = { permResident = 30 }
  topo-node stair_landing
  topo-node escalator_landing
}

PlatformLevel.tmap

topo-map PlatformLevel() {
  let params = { permResident = 15 }
  topo-node stair_landing
  topo-node escalator_landing
}

Valid stairs example

ConcourseStairs.ttr

transport ConcourseStairs is Stairs {
  let params = { turnBackCost = 3 }

  station Street at StreetLevel::stair_landing {
    location = 0.0,
    directSegmentIndex = 0
  }

  station Concourse at LowerConcourse::stair_landing {
    location = -4.0,
    directSegmentIndex = 1
  }

  station Platform at PlatformLevel::stair_landing {
    location = -8.0,
    directSegmentIndex = 2
  }
}

Invalid stairs example: missing segment index

station Platform at PlatformLevel::stair_landing {
  location = -8.0
}

Classification: Compilation-invalid. A stair station requires an integer directSegmentIndex.

Valid escalator example

PlatformEscalator.ttr

transport PlatformEscalator is Escalator {
  let params = { time = 18.0 }
  let displayName = "Platform escalator"

  station Concourse at LowerConcourse::escalator_landing {}
  station Platform at PlatformLevel::escalator_landing {}
}

The escalator has exactly two stations and a positive numeric traversal time.

Invalid escalator example: missing traversal time

transport PlatformEscalator is Escalator {
  let params = {}

  station Concourse at LowerConcourse::escalator_landing {}
  station Platform at PlatformLevel::escalator_landing {}
}

Classification: Compilation-invalid because params.time is required.

Invalid escalator example: three stations

transport PlatformEscalator is Escalator {
  let params = { time = 18.0 }

  station Street at StreetLevel::escalator_landing {}
  station Concourse at LowerConcourse::escalator_landing {}
  station Platform at PlatformLevel::escalator_landing {}
}

Classification: Compilation-invalid. An escalator currently connects exactly two distinct maps.

Related reference: Transport

11. Management Domains and Ride Policies

Scenario: A mixed-use tower contains three public floors, three office floors, and three hotel floors. One elevator physically serves all nine floors.

Real-place analogy: A management domain resembles the operational boundary between the retail podium, office landlord, and hotel operator. Each domain contains several separately named floors. A ride policy can describe movement between whole groups of floors without listing every floor pair.

Valid example

configuration.tcfg

building-includes {
  submap GroundLobby using StandardPublicFloor managed-by PublicDomain
  submap RetailLevel1 using StandardPublicFloor managed-by PublicDomain
  submap RetailLevel2 using StandardPublicFloor managed-by PublicDomain

  submap OfficeLevel10 using StandardOfficeFloor managed-by OfficeDomain
  submap OfficeLevel11 using StandardOfficeFloor managed-by OfficeDomain
  submap OfficeLevel12 using StandardOfficeFloor managed-by OfficeDomain

  submap HotelLevel20 using StandardHotelFloor managed-by HotelDomain
  submap HotelLevel21 using StandardHotelFloor managed-by HotelDomain
  submap HotelLevel22 using StandardHotelFloor managed-by HotelDomain

  vehicle MixedUseLift
}

GroundLobby, OfficeLevel11, and HotelLevel22 are map identifiers. PublicDomain, OfficeDomain, and HotelDomain are management-domain identifiers shared by three maps each.

root

root MixedUseTower(hasHotelAccess: Bool) {
  constraint HotelAccess {
    require hasHotelAccess
  }
}

The three reusable topo maps describe the standard topology for the floors in their respective domains.

StandardPublicFloor.tmap

topo-map StandardPublicFloor() {
  let params = { permResident = 30 }
  topo-node lift_landing
  topo-node public_corridor
  atomic-path [lift_landing <-> public_corridor] { cost = 8.0 }
}

StandardOfficeFloor.tmap

topo-map StandardOfficeFloor() {
  let params = { permResident = 120 }
  topo-node lift_landing
  topo-node office_corridor
  atomic-path [lift_landing <-> office_corridor] { cost = 10.0 }
}

StandardHotelFloor.tmap

topo-map StandardHotelFloor() {
  let params = { permResident = 90 }
  topo-node lift_landing
  topo-node guest_corridor
  atomic-path [lift_landing <-> guest_corridor] { cost = 12.0 }
}

MixedUseLift.ttr

transport MixedUseLift is Elevator {
  let params = {
    maxVelocity = 2.5,
    acceleration = 0.8,
    carAmount = 2
  }

  station LobbyStation at GroundLobby::lift_landing {
    location = 0.0,
    departureRate = 0.10
  }

  station Retail1Station at RetailLevel1::lift_landing {
    location = 4.0,
    departureRate = 0.10
  }

  station Retail2Station at RetailLevel2::lift_landing {
    location = 8.0,
    departureRate = 0.10
  }

  station O10Station at OfficeLevel10::lift_landing {
    location = 40.0,
    departureRate = 0.10
  }

  station O11Station at OfficeLevel11::lift_landing {
    location = 44.0,
    departureRate = 0.10
  }

  station O12Station at OfficeLevel12::lift_landing {
    location = 48.0,
    departureRate = 0.10
  }

  station H20Station at HotelLevel20::lift_landing {
    location = 80.0,
    departureRate = 0.10
  }

  station H21Station at HotelLevel21::lift_landing {
    location = 84.0,
    departureRate = 0.10
  }

  station H22Station at HotelLevel22::lift_landing {
    location = 88.0,
    departureRate = 0.10
  }

  ride-from PublicDomain to HotelDomain requires HotelAccess
  ride-from OfficeDomain to HotelDomain requires HotelAccess
}

OfficeDomain is a domain operand and matches all three office-floor stations. O11Station would be a station operand and match only the station on OfficeLevel11. OfficeLevel11 itself is a map identifier and is not a ride-policy operand.

Invalid example: using a map name as a ride-policy operand

// OfficeLevel11 is a map name, not a domain or station label.
ride-from OfficeLevel11 to HotelDomain requires HotelAccess

Classification: Compilation-invalid because OfficeLevel11 is neither a management-domain identifier nor a station label in this transport. To cover all three office floors, use OfficeDomain. To cover only the eleventh-floor station, use O11Station. Ride-policy operands are management domains, station labels, or any.

Related reference: Management Domain

12. Representing Uncertain Access

Scenario: A university skybridge has a card reader, but the map publisher cannot guarantee whether a particular visitor's card will be accepted.

Real-place analogy: The bridge physically exists and might be usable. It should not be represented as certainly open or certainly inaccessible when the available information supports neither claim.

Valid example

configuration.tcfg

building-includes {
  submap AcademicBuilding
}

root

root CampusNavigation(hasBridgeCard: Bool) {
  constraint BridgeCardAccess {
    require hasBridgeCard
  }
}

AcademicBuilding.tmap

topo-map AcademicBuilding() {
  let params = { permResident = 350 }

  topo-node atrium
  topo-node indoor_detour
  topo-node skybridge_door
  topo-node library_link

  atomic-path [atrium <-> indoor_detour] { cost = 20.0 }
  atomic-path [indoor_detour <-> library_link] { cost = 20.0 }

  atomic-path [atrium <-> skybridge_door] { cost = 8.0 }
  atomic-path [skybridge_door <-> library_link] { cost = 8.0 }
    subject-to BridgeCardAccess because "The skybridge door may require a compatible university card."
}

The uncertain path remains represented with its failed or satisfied access condition. The TopoNavi Engine can prefer the confirmed detour and disclose the skybridge uncertainty when an uncertain route is considered.

Invalid example: combining hard and uncertain access

atomic-path [skybridge_door <-> library_link] { cost = 8.0 }
  requires BridgeCardAccess
  subject-to BridgeCardAccess because "The door may require a compatible university card."

Classification: Compilation-invalid. The same element cannot use both requires and subject-to. Use requires for hard exclusion or subject-to for explicitly uncertain availability.

Related reference: Parameters and Constraints

Validation and Error Reporting

A TopoScript project is valid when its selected sources can be parsed, elaborated, evaluated, and linked into a compiled building model.

Successful compilation establishes structural language validity. It does not guarantee that every real-world route is available, that application-defined annotations are accurate, or that the modeled venue remains unchanged.

Validation Scope

Project validation covers:

  • the whole-building configuration and selected project sources;
  • lexical and grammatical correctness;
  • name resolution, scopes, types, and expression evaluation;
  • topo-map nodes and paths;
  • transport declarations, stations, and ride policies; and
  • cross-file references required to construct the navigation and transport graphs.

Route availability for a particular origin, destination, access context, or routing preference is a routing result rather than a project-validity test. See No-Route Outcomes.

Validation Phases

  1. Project loading and composition: resolve the configuration, root source, selected topo maps, reusable map bases, and transports.
  2. Parsing: recognize TopoScript tokens, expressions, declarations, and source-specific top-level forms.
  3. Elaboration and evaluation: resolve visible names, check expression types, evaluate parameters and constraints, and construct map and transport declarations.
  4. Graph construction and linking: build per-map navigation graphs, resolve qualified station endpoints, validate transport-specific invariants, and construct the cross-map transport graph.

The distinction between source declarations, compilation, and route planning is defined in Language Lifecycle.

Common Invalidity Classes

Class Examples Governing reference
Syntax Invalid tokens, malformed declarations, incomplete expressions, or the wrong top-level source form. Lexical Structure and the syntax section for the relevant declaration.
Names and types Unknown symbols, invisible local names, incompatible expression types, missing record fields, or a non-Boolean constraint. Identifiers and Qualified Names, Name Scopes and Visibility, and Types.
Project composition Missing selected sources, unresolved reusable bases, invalid cross-file references, or mismatched project names. Whole-Building Composition.
Topology Unknown path endpoints, missing path cost, invalid direction declarations, or malformed topo-map data. Topo Maps, Nodes, and Paths and Local Movement.
Transport Unknown landing nodes, invalid station fields, unsupported transport types, invalid service ranges, or conflicting ride policies. Cross-Map Transportation and the type-specific elevator, escalator, or stair article.

Current Reporting Limits

Parsing failures may identify and highlight a source position. Errors discovered during later compilation phases may provide only a human-readable description without an attached source range.

Validation may stop after reporting one failure. A single run is not guaranteed to return every independent problem in the project.

Human-readable error text is intended to help authors correct their source, but its exact wording is not a stable API. Applications and editor integrations must not use message text as a persistent diagnostic identifier.

Correcting an Invalid Project

Missing Path Cost

Every atomic path requires a numeric, non-negative cost.

Invalid:

atomic-path [lobby -> reception] {
  tags = ["indoor"]
}

Corrected:

atomic-path [lobby -> reception] {
  cost = 6,
  tags = ["indoor"]
}

See Path Cost.

Unknown Transport Landing

A station must reference an existing node in a compiled map.

Invalid when Lobby does not declare main_lift:

station LobbyStop at Lobby::main_lift {
  location = 0.0,
  departureRate = 0.25
}

Corrected using the landing node declared by the map:

station LobbyStop at Lobby::main_elevator_landing {
  location = 0.0,
  departureRate = 0.25
}

See Stations and Landing Nodes.

Non-Boolean Constraint

The expression required by a constraint must evaluate to Bool.

Invalid:

root Building(officeAccess: Int) {
  constraint OfficeAccess {
    require officeAccess
  }
}

Corrected:

root Building(officeAccess: Bool) {
  constraint OfficeAccess {
    require officeAccess
  }
}

See Global Constraints.

Invalid Escalator Service Range

An escalator must contain exactly two stations belonging to two distinct maps.

Invalid:

transport AtriumEscalator is Escalator {
  let params = { time = 18.0 }

  station Lower at Mall2::escalator_landing {}
  station Middle at Mall3::escalator_landing {}
  station Upper at Mall4::escalator_landing {}
}

Corrected:

transport AtriumEscalator is Escalator {
  let params = { time = 18.0 }

  station Lower at Mall2::escalator_landing {}
  station Upper at Mall3::escalator_landing {}
}

See Escalator Stations.

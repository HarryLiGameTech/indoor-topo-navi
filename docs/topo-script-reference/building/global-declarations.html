Building-Global Declarations and Compilation Inputs

The optional extensionless root source establishes declarations shared by every topo map and transport in one TopoScript project. It does not create a map, node, path, transport, or navigable building area.

Project membership remains the responsibility of building-includes. For the general relationship among buildings, maps, transports, parameters, and constraints, see Major Language Entities and Their Relationships.

The Root Source

The root source is named root and contains one root declaration:

root SkyrimTower(
  officeAccess: Bool,
  tradingFloorAccess: Bool,
  carryingWeight: Float,
  timeOfDayInSeconds: Int
) {
  // Building-global declarations
}

The identifier after root names the compiled root declaration. If a project needs neither declared compilation inputs nor shared declarations, the root source may be omitted. Source discovery and project layout are defined in Project Sources.

Documented Global Declarations

Declaration Purpose
Root parameter Names an external value expected for compilation.
def Defines a shared function or calculated value.
constraint Gives one or more Boolean requirements a reusable name.

Root-level let and type declarations are present in the current parser, but their intended long-term global role is under design review. They are not part of the stable building-global surface documented here.

Although the shared body grammar can parse some topology or transport constructs inside a root, the root compiler does not elaborate them. Nodes, paths, stations, and ride-from declarations must be placed in their respective map or transport sources.

Compilation Inputs

Root parameters declare values that the containing application is expected to supply when compiling the project:

root SkyrimTower(
  isInEmergency: Bool,
  officeAccess: Bool,
  carryingWeight: Float,
  timeOfDayInSeconds: Int
) {
}

The reliably supported external parameter types are Bool, Int, Float, and String. Their language meanings are defined in Primitive and Domain-Specific Types.

The API compiler accepts host Boolean, integer, long-integer, single-precision floating-point, double-precision floating-point, and string values. Lists, records, functions, and arbitrary host objects are not currently accepted as external compilation inputs.

Required Values and Defaults

TopoScript does not currently provide parameter-default syntax. Default values are planned for a near-term language update.

The following intended form is not yet valid:

root Building(
  officeAccess: Bool = false
) {
}

Until defaults are implemented, an application should supply every declared parameter used by the project.

The current compiler does not yet validate the root parameter list as a strict invocation contract:

  • a missing parameter is detected only if evaluation reads it;
  • an unused declared parameter may be omitted without an error;
  • an undeclared extra parameter is accepted and becomes visible to child sources;
  • a supplied value is not checked directly against the type written in the root parameter list.

These behaviors are implementation limitations, not recommended authoring practices. Applications should supply exactly the declared parameters with values matching their declared types.

Global Functions

A root-level def defines reusable calculation logic visible to maps and transports:

root RunningExample() {
  def timeWhenRushing(stdCost: Float, timeToRun1KmInSeconds: Int): Float = {
    stdCost * (timeToRun1KmInSeconds / 300) // Assume 1km=5mins is the standard pace
  }
}

A map can use the function when calculating path data:

topo-map Concourse() {
  let params = {}

  topo-node north_entrance
  topo-node platform_lobby

  atomic-path [north_entrance <-> platform_lobby] {
    cost = timeWhenRushing(10.0, 240)
  }
}

Function definitions are evaluated according to their dependency graph rather than their textual order. A cyclic dependency fails compilation. Parameter annotations participate in function construction, while declared return types are parsed but are not yet consistently enforced.

Global Constraints

A constraint gives a Boolean compilation requirement a reusable name:

root SkyrimTower(
  officeAccess: Bool,
  carryingWeight: Float
) {
  constraint OfficeAccess {
    require officeAccess
  }

  constraint CarryingGoods {
    require carryingWeight > 0.0
  }
}

Every require clause must evaluate to Bool. Multiple clauses form a conjunction:

constraint AuthorizedOfficeDelivery {
  require officeAccess
  require carryingWeight > 0.0
}

AuthorizedOfficeDelivery is satisfied only when every clause is true. An empty constraint is currently accepted and evaluates to true, but should be avoided because it communicates no policy.

A complete applied example is available in SkyrimTower’s Operational Access Inputs.

Constraint Visibility

A root constraint is visible to every compiled topo map and transport. A child-local declaration may shadow a global name. The general scope rules are defined in Name Scopes and Visibility.

A constraint has no effect merely because it exists. It affects the compiled building only when referenced by an access annotation or ride policy.

atomic-path [public_hall <-> staff_hall] {
  cost = 4.0
} requires OfficeAccess
station F50 at OfficeLevel50::passenger_lift {
  location = 222.0,
  departureRate = 0.055
} requires TradingFloorAccess on Arrive
ride-from any to OfficeDomain requires OfficeAccess

Constraint Evaluation Order

Root constraints are evaluated during compilation and in source order. They should depend directly on supplied compilation parameters and literals.

In the current implementation, root constraints are evaluated before root-level function definitions. A root constraint therefore cannot call a root def, even if the function appears earlier in the source. This differs from map-local and transport-local constraints, which are evaluated after their local definitions.

A constraint may refer to a previously evaluated constraint, but directly listing the required predicates is usually clearer. A reference to a later constraint is unresolved at the time of evaluation.

Effects of Hard Constraints

Attachment Effect when unsatisfied
Atomic path The path is omitted from the compiled topology.
Unscoped station requirement Both arrival and departure are prohibited.
Station requirement on Arrive Arrival is prohibited; departure remains possible.
Station requirement on Depart Departure is prohibited; arrival remains possible.
ride-from requirement Matching directed transport rides are omitted.

These are compile-time effects. Detailed attachment semantics belong to the topology, transport, and routing articles. A subject-to annotation is different: it records uncertain access rather than enforcing a hard prohibition. The tutorial examples compare the two models in Representing Uncertain Access.

Management Domains

A management domain is a building-global map classification, but it is not declared as a root value. A domain name is introduced by assigning it to a submap:

building-includes {
  submap Lobby managed-by PublicDomain
  submap OfficeLevel28 managed-by OfficeDomain
}

A topo map may replace its configured domain:

topo-map OfficeLevel28() override-managed-by TradingDomain {
  let params = {}
  topo-node elevator_lobby
}

The effective domain is the topo-map override when present, otherwise the configuration assignment, otherwise the fallback domain Misc. Each compiled map has one effective domain.

Domain attachment is introduced in Management-Domain Attachment. A realistic multi-domain example is provided by Management Domains and Ride Policies.

Access and Ride-Policy Model

TopoScript has no standalone global access-policy declaration. The model combines:

  1. a global or local named constraint;
  2. a requires attachment on a path or station; or
  3. a ride-from declaration inside a transport.
root Building(hasHotelAccess: Bool) {
  constraint HotelAccess {
    require hasHotelAccess
  }
}
ride-from any to HotelDomain requires HotelAccess

The root defines the reusable condition. The map or transport defines where that condition applies.

Building Metadata and Global Tags

TopoScript currently has no dedicated building-metadata declaration for an address, operator, display name, geographic location, publication version, or similar project-level information. Such information must be maintained by the containing application or project package.

There is likewise no global tag declaration or tag registry. Tags appearing in node or path records are application-facing annotation values rather than globally declared language entities. See Stability Boundaries.

Global Names

Parameter, function, and constraint names belong to the root’s project-global scope. Authors should keep each name unique and avoid collisions between declaration categories.

The current compiler may silently replace colliding global bindings. Name collision must not be used as a policy mechanism. Child-local shadowing is supported by the general lexical-scope model, but should be deliberate and clearly documented.

Compilation Time and Routing Time

Root parameters and constraints are evaluated while compiling the building:

TopoScript sources
        +
compilation-input values
        |
        v
fixed compiled graph and access state
        |
        v
one or more route requests

A route request does not independently re-evaluate root constraints. Changing officeAccess, timeOfDayInSeconds, or another compilation input requires a separately compiled result for that input context.

Routing preferences and banned tags belong to the route request rather than the root. The full lifecycle is defined in Language Lifecycle.

Effects on the Compiled Building

Global feature Possible effect
Parameter Supplies data used by expressions and constraints.
def Supplies reusable calculation logic used during map or transport construction.
Constraint attached to a path Changes graph connectivity.
Constraint attached to a station Changes arrival and departure permission.
Constraint attached to ride-from Changes available directed transport rides.
Management domain Changes which maps match a domain-based ride policy.
Unused declaration Has no direct effect.

Global declarations are not returned as navigable route steps. Their observable result is the building model produced from them.
